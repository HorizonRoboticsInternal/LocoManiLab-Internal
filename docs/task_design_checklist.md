# Benchmark 任务设计注意事项与逐项检查清单

最后更新：2026-09-10

## 1. 用途与强制执行方式

本文档总结当前工作区已有任务讨论、实现记录和回归结果中反复出现的问题。凡是**新增、修改、扩展或评审 benchmark 任务**，都必须先完整阅读本文档，再从第 4～10 节选择与本次改动直接相关的检查项。阅读完整清单不等于执行其中所有测试；无关项应标为 `N/A`，不能为了“更全面”而自动扩大验证范围。

任务设计不能只给出任务名称和自然语言描述。交付时应附带第 11 节所示的简短“检查结论”，只汇报本次改动、实际执行的检查、未验证项和剩余风险。只有复杂新任务、共享 primitive、自由物体/随机布局或复合状态机才逐项填写详细模板；其中无关项标为 `N/A`。

存在未解决的物理可行性、重复注册、初始即成功或成功条件不可验证问题时，不得把任务标为“可实现”或“已完成”。除此之外，验证以足以覆盖本次风险为停止条件；默认快速路径应在几分钟内完成，而不是持续增加重复次数来获得边际证据。

### 1.1 验证范围

运行时验收只覆盖本次新增或真正改变的行为路径：

- 场景扩展默认只实例化新增 Scene；原有 Scene 的代码、规格和成功条件未变时，不重复运行。
- 多个镜像任务若共享同一初始化与场景装载路径，可共用一次场景 smoke 证据；只分别测试它们不同的目标状态或谓词。
- 修改共享 primitive 时，先列出直接消费者，再按不同消费方式选择最少代表任务；不按消费者数量做全排列回归。

不得默认把 reset、物理稳定性、成功/反例、人工操作或采集适配扩展为“旧任务 + 新任务”的整个房间、整个 catalog 或全仓库回归。注册与去重可以对所属 catalog 做**不实例化旧环境**的静态审计。只有用户明确要求，或已经出现无法用定向测试隔离的跨任务故障时，才执行运行时全量检查。

### 1.2 阶段边界：Git 交付时不重复验证

本清单只用于任务设计、实现和语义评审阶段。用户仅要求暂存、提交、推送、切换分支、cherry-pick、rebase 或合并已经设计并验证过的任务改动时，不得因为提交里包含任务文件而重新执行第 4～10 节。

Git 交付阶段直接复用设计阶段已有的验证记录，不重新运行语法检查、pytest、catalog 审计、headless reset、成功/反例测试、GUI 操作或数据采集。该阶段只检查 Git 交付本身：分支和远端状态、暂存内容、提交身份与范围、冲突以及 fast-forward 条件。若没有可用的验证记录，应在交付说明中标明“本轮未验证”，而不是自行补跑。

只有在 Git 整合中实际修改任务代码，或冲突处理改变了任务语义、初始化、场景规格、成功条件或注册入口时，才对直接受影响任务重新执行本清单。纯文本冲突和不改变任务语义的机械整合不触发任务验证。

### 1.3 修改边界：未经明确要求，不得连带修改其他任务

未经用户明确要求或批准，不得连带修改其他任务。修改范围以用户明确指定的任务及场景为准；原子/复合关系、共享初始化、YAML 锚点、继承关系或资产复用均不构成扩大修改范围的授权。本条约束同样适用于下文的共享资产一致性、兼容性和缺陷修复要求。

- 修改共享代码、规格或资产前，先识别所有受影响任务；优先使用目标任务专用覆盖、规格深拷贝或私有实现隔离改动，确保范围外任务的实际行为不变，而不只是其文件未被直接编辑。
- 已采集数据的任务作为冻结基线。未经明确授权，不得改变其名称、支持场景、资产及物理配置、物体与机器人初始化、成功条件，也不得修改已有数据文件。修复复合任务不能默认同步修改对应原子任务，反之亦然。
- 若无法隔离改动，或发现其他任务也存在问题，应先说明涉及的任务、必要性及对已有数据的影响，取得用户明确批准后再修改；不能以“顺手修复”“保持一致”或“测试通过”为由自行扩展范围。
- 修复指定任务时，须核对代码、规格及共享依赖的前后差异，确认其余任务的场景、初始化、任务内容和成功条件均未改变；其余任务一律按可能已采集数据保护。必要时做定向回归，不自动扩大运行时验证范围。

## 2. 本清单从当前工作区提取出的核心教训

1. **自然语言不同，不代表物理任务不同。** 曾出现 Storage、Drawer、Bedside Drawer 等不同名称实际指向同一个 fixture/joint 的重复任务。
2. **任务名必须描述真实机构。** 抽屉平移、门铰链、洗衣篮盖、纸箱翻板和笔记本盖不能混为笼统的 Open/Close Storage。
3. **场景里存在资产，不代表 G1 能操作。** 高处柜门、原始位置过高的保险柜、被椅子挡住的桌面都曾造成不可达任务。
4. **语义状态可能与真实物理方向相反。** iTHOR 笔记本关节的真实开/合方向与通用语义解析默认值相反，必须从实际关节运动验证。
5. **初始化是任务的一部分。** 机器人脚底越界、手臂侵入桌面、出生碰撞、出生即成功、物体朝向不利于抓取以及 reset 后关节自行运动，都会让任务失效。
6. **“看起来放进去了”不是可靠成功条件。** 仅检查中心或高度会把倚靠碗沿、贴外壁、穿到底部、仍被夹爪抓住等状态误判为成功。
7. **复合任务必须验证顺序。** 只检查最终状态会让机器人跳过导航阶段，或按错误顺序完成仍然成功。
8. **隐藏导出不等于注销。** 仅从 `__all__` 删除类不会移除 robosuite 环境注册；重复类、废弃类和实现基类仍可能成为隐藏启动入口。
9. **无可观察物理变化的任务不应进入正式套件。** 静态 light switch 只有内部布尔值变化、没有关节或外观/灯光变化，已因此被移除。
10. **人工全流程是独立证据，不是默认门槛。** Headless 检查不能冒充人工操作；只有用户要求 GUI、teleop、采集就绪或改动直接涉及交互可达性时才执行，否则如实标为未验证。
11. **旧记录可能过时。** `docs/collect_data&visualize.md` 的早期场景范围和当前正式 catalog 可能不同；任务数量、导出列表和采集脚本适配状态也会随实现变化。
12. **原有任务需要明确保护。** 场景扩展不能无意破坏已发布任务的注册名和校准意图；必要时用差异审计和定向回归证明兼容性。发现范围外任务的成功判定漏洞应先报告并请求授权，不得自行连带修复。
13. **验收范围不能自行扩大。** 优先使用静态注册、代码差异和代表性 smoke；没有具体失败信号时，不增加 reset 次数、不做全场景谓词排列，也不重复已通过的测试。

## 3. 信息源优先级

设计前先核对信息是否仍然有效，按以下优先级判断：

1. 当前实际代码、场景资产、环境注册表和可重复的运行结果；
2. 最新且带日期、带验证证据的任务文档；
3. 较早的说明、示例命令和对话记录。

若三者冲突，不得默默选择其一。必须在设计结论中指出冲突，以代码和实测为准，并同步修正文档。任务矩阵中的 `- [ ]` 只表示“数据尚未采集”，不能被当成任务未实现或未验证。

## 4. 任务定义检查

- [ ] 明确房间类型、准确 Scene ID、原子/复合任务类别以及支持场景集合。
- [ ] 用一句话写清操作者、目标实体、动作、目标状态和必要顺序。
- [ ] 指令中的家具/物体名称能在仿真和现实中指向同一类可观察实体，不依赖绿色区域或隐藏坐标提示。
- [ ] 任务具备真实、可观察的场景状态变化；纯内部变量变化不能作为正式任务。
- [ ] 任务名称准确反映物理机构：Drawer、Door、Hamper Lid、Box Flap、Laptop Lid 等分别命名。
- [ ] 原子任务只包含一种核心技能；复合任务明确拆出阶段和每阶段完成条件。
- [ ] 明确哪些旧任务、场景和文件受保护，以及允许变更的边界。
- [ ] 每类房间先指定一个主场景，并优先把不重复的任务集中在该场景；当前 Bedroom 主场景为 329，Bathroom 主场景为 401。其他场景只保留原有兼容任务或主场景确实没有的物理机构，不能仅为扩大 Scene 数量复制同一任务。

## 5. 去重、命名与注册检查

- [ ] 先盘点当前公开任务、`__all__`、包级导入和 robosuite/房间环境注册表，再决定是否新增。
- [ ] articulation 按以下物理签名去重：`Scene ID + fixture stable ID + joint + open/close 目标状态`。
- [ ] navigation 至少按 `Scene ID + 目标 fixture stable ID` 去重，并确认两个别名没有指向同一碰撞实体。
- [ ] pick/place、lift、push 除名称外还要比较实际源物体模型、容器/目标模型、支撑面、初始布局和目标谓词，避免语义重复。
- [ ] 同一任务物品必须在所有前后关联任务中保持一致。当前正式固定小物 Can、Boxed Food、Mug、Bar Soap 各自只能映射到一份 canonical MJCF/scale/有效抓持跨度/质量与碰撞配置，并在原子与复合任务中复用；不能在另一个任务里重新选同类随机资产或重写倍率。场景原生物体保留其明确 stable ID，但同一原生物体被多个任务复用时也不得改变尺寸或物理配置。初始位姿可以因“横放后立起”等明确任务语义或支撑面方向而不同，但优选抓取轴必须一致并记录。确需不同变体或尺寸时，应使用明确区分的新物品身份并记录物理原因。
- [ ] 原子任务与复合任务分别去重；复合任务还要比较阶段顺序，A→B 与 B→A 可以是不同任务，但必须真的强制顺序。
- [ ] 通用类不能跨场景混合不同物理机构；必要时拆成按机构或按场景命名的类。
- [ ] 废弃任务不能只从 `__all__` 隐藏：删除其类定义/导入，或明确从所有注册表注销。
- [ ] 私有实现基类不能以隐藏环境名留在注册表中。
- [ ] 类名、`SUPPORTED_SCENE_IDS`、`SCENE_SPECS`、包导出、注册名、文档和启动命令完全一致。
- [ ] 统计每个场景的原子/复合任务数；数量目标只能在物理可行、非重复的前提下满足，不能为凑数保留坏任务。
- [ ] 当前语义收敛允许 Bedroom 仅保留 19 个 atomic、Bathroom 仅保留 16 个 atomic；后续只能用符合房间语义且物理不重复的新任务补足，不能恢复已删除 PnP 凑数。

## 6. 物理可行性与仿真—现实对齐检查

- [ ] 用 stable ID 定位真实 fixture、joint、支撑面和目标物体，不能只依赖模糊 token 的首次匹配。
- [ ] 确认目标 joint 确实存在、可动、运动方向正确，并能产生可观察的外观变化。
- [ ] 实测目标交互点高度、机器人站位、双手可达性、碰撞空间和所需动作幅度。
- [ ] 检查桌边、墙、床、柜体、椅子等是否阻挡机器人底盘、手臂或目标关节完整运动。
- [ ] 若必须移动/垫高 fixture，检查新位置的地面支撑、基座碰撞体、AABB 接合、周围净空和现实可复现性。
- [ ] 若必须移除阻挡资产，只在相关任务模型中按精确 stable ID 移除；用规格与代码差异确认没有扩大删除范围，只对本次任务或直接受影响任务做运行时回归。
- [ ] 支撑面尺寸、物体/容器缩放、边缘净距和容器开口足以完成操作；不能只验证模型能生成。
- [ ] 不可达、无关节、无视觉反馈或无法现实复现的任务应删除或重新设计，而不是放宽成功条件掩盖问题。

### 6.1 抓取任务的人机工效基准

- [ ] 小型手持源物体以 `0.075 m` 的有效抓持跨度为默认设计目标；验收要求严格大于 `0.07 m` 且不超过 `0.08 m`。这里的“抓持跨度”是夹爪实际闭合方向上的物体尺寸：圆形/圆柱体取主体直径，细长物体取适合横向夹持的短轴或中轴，不能一律使用最长 bbox 边。篮子、大容器及其他明显的大件不套用该范围，应按真实把手、边沿或主体抓取部位和机器人工作空间单独校准；每个豁免都要记录实际抓取部位、有效跨度和不能按该范围缩放的物理原因，不能静默豁免。
- [ ] 无导航的抓取/Lift/Pick-and-place 任务可以把机器人根节点到源物语义中心的水平距离 `0.40 m` 作为初始布局参考，但不将固定距离或统一容差作为验收门槛。强制标准是：reset 后机器人与桌边及目标 fixture 零碰撞，固定 base、只操作双手就能抓住源物，并能完成该任务的最终放置或抓起状态。每个 `task×scene` 必须独立校准，记录实测的机器人—源物水平距离、双手可达性证据和最终放置可达性；不能用机器人到桌边、fixture 中心或 region 中心的距离代替。多源物任务要证明全部源物在固定 base 时可达；带导航任务使用远端出生合同，并另行校准到达后的操作位。
- [ ] 必须先读取固定资产的原生 bbox/碰撞尺寸，再计算任务 scale；禁止把所有资产机械乘同一个 `1.5`。若按 7.5 cm 会使带把手杯子、盒装物或其他非等轴物体的长边不合理，应保留真实外形比例并选择最接近 7.5 cm 的可抓横向尺寸。
- [ ] Bowl、Basket、Bin 等容器不套用 7.5 cm 源物标准。容器按源物尺寸、开口、稳定性和桌面空间独立校准，必须能容纳目标且留有实际投放余量；完整纸卷、喷雾瓶、Scrub Brush 和 Lift Basket 等大件按真实抓取部位记录豁免，不能因统一倍率放大到超出工作空间。
- [ ] 同一固定资产在原子与复合任务中复用同一个 scale 常量；场景 YAML 不得用隐式 `*_scale` 覆盖制造跨场景尺寸差异。确需场景特例时，必须记录物理原因并单独验证。
- [ ] 抓取与放入任务优先使用该场景面积更大、操作高度合适的主书桌/大桌面；只有任务语义本身要求 A→B 搬运、场景没有可用大桌面或大桌面物理不可达时，才使用床头柜或窄边桌，并在设计结论中说明原因。
- [ ] 源物和容器应完整落在桌面内，中心位于同一条沿桌边的直线上，深度一致；长宽比不小于 `1.15` 的源物和容器长轴应平行桌边（即与机器人到物体的视线近似垂直）。在保留完整 footprint 和必要净距的前提下，选择最靠近机器人一侧的真实可接触位置。
- [ ] 原子与对应 `WalkAnd*` 复合任务应复用同一命名工作面、物体 scale、近边行布局和朝向能力；导航任务只改变机器人远端出生与阶段状态机，不应悄悄换到另一张更小的桌子。
- [ ] 共享资产的一致性检查必须双向覆盖：修改任一原子或复合任务的模型、scale、质量/碰撞配置或优选抓取轴时，先枚举全仓库内同一 MJCF 资产的全部消费者并评估影响；不能只检查同房间或同任务族。枚举消费者不等于获得修改授权；需要同步修改范围外任务时，必须按第 1.3 节先取得用户明确批准，否则隔离改动或暂停实施。

## 7. 初始化与 reset 检查

### 7.1 机器人

- [ ] 机器人中心及半径 `0.25 m` 的八方向脚底采样点全部位于 Floor 内。
- [ ] 初始状态碰撞数为 0，双手/夹爪不侵入桌面、家具或目标物体。
- [ ] 出生点不会满足成功条件；navigation 出生距离应比成功阈值至少多 `0.15 m`。
- [ ] 纯导航任务应在可通行的空旷区域使用逐场景精确出生位姿，并在零碰撞和完整 Floor 脚印的前提下尽量拉长有效行程；不得在 reset 时从一组近距离候选中选择首个可行点。
- [ ] 出生点附近确需清障时，只能按 YAML 中的精确 stable ID 移除妨碍通行的小物体，并记录移除清单；不得移除目标、主要家具或使用类别猜测。
- [ ] 机器人朝向真实交互点，且从出生点到操作位存在可通行路线。
- [ ] 只有本次改动涉及位置抖动，或首次 reset 暴露不稳定时，才增加有限重复；若抖动导致碰撞、越界或手部侵入，则关闭抖动或约束采样域。
- [ ] 复合任务的远端出生点不能复用为近桌物体布局的操作者参考点。
- [ ] reset 完成时机器人必须处于控制器可保持的静态平衡：自由关节高度已校准、基座和关节速度已清零或受控、零碰撞、完整脚印在 Floor；不能依靠 reset 后自动后退、跌落或碰撞反弹进入合法状态。

### 7.2 物体、容器与关节

- [ ] 所有物体稳定落在指定支撑面上，无悬空、穿模、初始相交或 reset 后滚落。
- [ ] 物体位于可抓取/可推动区域，并为较大物体保留明确桌边净距。
- [ ] 细长物体的长轴朝向利于 G1 抓取；当前经验规则是长宽比不小于 `1.15` 时，使长轴与“操作位→物体”视线垂直。
- [ ] 放入任务的源物体和容器按真实操作侧布局；需要近边并排时，二者深度一致、中心连线平行桌边。
- [ ] 固定模型和缩放在运行时确实加载，没有被 group 随机采样或其他配置覆盖。
- [ ] articulation 的初始关节状态与目标状态相反；同时清零关节速度并检查重力、阻尼和摩擦不会让它自行完成任务。
- [ ] 复合任务的初始开度以导航等待期间稳定、可操作为准，不必机械遵循 20%/80%；不稳定时可自行调整，但须在对应复合任务内隔离并验证，保持阶段顺序和最终成功条件不变，不得连带修改已采集的原子任务、共享场景资产或数据。
- [ ] 本次新增或修改的随机化先做少量 reset；只有出现波动时才逐步增加次数，并保证零碰撞、初始失败和可操作性。
- [ ] 自由物体与容器在 reset 返回时就必须真实浅接触命名支撑、无非法穿透、速度清零并保持合理姿态；不能以“稍后会自然沉降”为初始化策略。
- [ ] 对本次改变的自由物体路径做一次短时独立稳定检查：机器人保持不动时，物体不得滚落、掉下桌面、明显漂移或失去命名支撑。只有观察到波动时才按第 10.2 节增加 reset 或 settle 次数。

## 8. 成功条件与防误判检查

所有 Bedroom / Bathroom 正式任务的最终成功状态必须连续保持 `1.0 s`，并按环境实际 `control_freq` 换算控制步数；条件中断立即清零。复合任务的中间阶段可以使用更短的任务专属门槛，但最终状态不能只保持固定 5 步。

### 8.1 Navigation

- [ ] 使用机器人碰撞几何到指定家具可碰撞几何的最短距离，不用家具中心距离代替。
- [ ] 每个 `task×scene` 显式记录最小出生碰撞距离，并在 reset 后复测；中心距离只可作为诊断 metadata，不能替代碰撞距离验收。
- [ ] 当前 Bedroom / Bathroom 经验距离阈值为不超过 `0.35 m`。若这是任务的最终导航目标，满足距离条件后必须连续保持 `1.0 s`；若只是复合任务的中间导航阶段，可以显式使用任务专属的 5 步门槛。修改距离或中间阶段时长时，必须说明现实测量方式和回归证据。
- [ ] 目标家具是实际可接近的碰撞实体；例如洗手盆本体不可接近时，应明确使用其下方柜体，而非错误地放宽距离。

### 8.2 Articulation

- [ ] 成功绑定指定 joint，而非同 fixture 上的任意关节。
- [ ] 通过实际 `qpos` 极限和外观验证 open/close 方向，不盲信通用语义默认值。
- [ ] 目标开度阈值合理，且需要保持；初始状态、重力漂移和机器人未接触都不能触发成功。
- [ ] Drawer 使用短行程：Open 从 20% 开度开始，到 80% 判定完成；Close 从 80% 开始，到 20% 判定完成。
- [ ] 小门（例如保险柜门）使用 20%↔80% 行程。大型通行门使用真实角度：Open 从 0° 到 30°，Close 从 30° 回到 0°；关闭可以使用不超过 2° 的明确校准容差。Laptop Lid、Hamper Lid、Box Flap 和 Toilet Lid 不是大型通行门，必须按各自机构单独定义。

### 8.3 Lift / Push / Pick-and-place

- [ ] Lift 要求先有 G1 手闭合并接触物体，再相对 reset 后稳定高度上升至少 `0.30 m`；达到高度后必须持续抓持并保持最终成功状态 `1.0 s`。
- [ ] Push 要求先由手接触，从物体真实 post-placement 起点计算位移，并检查进入/接触命名目标；目标自身不能被一起推走，完成时手应释放或离开。
- [ ] 放入容器同时检查：源物体与命名容器实体接触、水平居中、物体底部位于容器内部并低于口沿、夹爪释放、连续保持。
- [ ] 倚靠容器边缘、贴外壁、穿到容器底下、容器被碰走、物体仍在夹爪中等反例必须失败。

### 8.4 Composite

- [ ] 为每阶段维护显式状态机，必须按设计顺序完成。
- [ ] 在未完成导航阶段时直接操纵最终目标不能成功；到达错误目标或颠倒顺序也不能成功。
- [ ] 阶段切换后使用正确的近端操作位和目标实体，不被旧阶段缓存坐标误导。

## 9. 实现、兼容与文档检查

- [ ] 优先复用已经验证的 task primitive/mixin，但逐项覆盖场景特有 fixture、joint、开合方向、站位和成功阈值。
- [ ] 场景特例显式记录，避免把一个场景的坐标、缩放或资产 ID 当作所有场景通用值。
- [ ] 公开环境提供准确的 episode metadata：语言、目标实体/模型、阶段顺序和成功定义。
- [ ] Kitchen 和 Living Room 的任务语言指令 `lang` 直接定义在各自任务类中，不得写入 YAML 或集中语言表；其 YAML 只保存场景与校准参数，场景特有措辞也在任务类中处理。未经明确要求，不将这项迁移扩展到其他房间。
- [ ] 检查 import/注册副作用；导入模块后不存在意外公开或隐藏环境。
- [ ] 用代码差异确认受保护旧任务未被意外修改，并静态核对其原注册名；只有旧任务被本次修改直接影响时才做相应定向行为回归。
- [ ] 同步更新任务总表、场景支持矩阵、原子/复合分类、启动命令和验证状态。
- [ ] 旧文档与代码冲突时立即修订；不要传播过时的场景范围或任务数量。
- [ ] 使用数据采集脚本前确认它已适配该任务；当前已知 `collect_fixed_task` 的旧记录明确提示尚未适配 `IThorLivingRoomCloseLaptop`。

## 10. 风险分级验证

默认目标是用最少证据确认本次改动正确，通常应在几分钟内完成。快速路径全部通过后就停止；“还能再测”不是继续扩大验证的理由。已有且仍适用的结果可以直接复用。

### 10.1 默认快速路径

仅执行下列与改动相关的项目：

1. 检查代码/spec 差异、任务物理签名和受影响入口。
2. 只编译或导入改过的模块；仅当 spec、注册、导出或矩阵变化时运行所属 catalog 的静态审计。
3. 对每条**新增或改变的场景初始化路径**做 1 次 headless reset，检查能构建、初始不成功、机器人无碰撞且脚印在 Floor。场景扩展不重跑未改的旧 Scene。
4. 对每个改变的成功谓词做 1 个正例和 1 个最关键反例。优先写快速单元测试；谓词不依赖场景几何时，只选一个代表 Scene 做物理验证。
5. 运行 `git diff --check` 并同步简洁任务清单。自然语言、注释或文档变更不触发 MuJoCo 回归。

推荐命令：

```bash
python validate_ithor_tasks.py --resets 0

python validate_ithor_tasks.py \
  --task-filter <本次任务名片段> \
  --scene-filter <新增或改变的 Scene ID> \
  --resets 1

pytest -q <相关测试文件> -k <本次功能>
```

静态 catalog 审计可以读取旧任务信息来发现重名、隐藏注册和重复签名，但不得实例化旧任务。若仓库已有更小的专用审计，应优先使用专用审计，不为简单改动运行整份大型测试文件。

### 10.2 何时才升级验证

只有出现以下具体风险或失败信号时才增加检查：

- 本次引入随机采样、自由物体、支撑接触、狭窄站位或曾出现间歇失败：先将相关路径增加到 3 次 reset；修复后仍有波动时再增加到 5 次。
- 只有用户明确要求，或已经复现低频故障并需要估计发生率时，才运行 20 次以上 reset。
- 只有本次涉及自由物体、动态支撑或已经观察到漂移时，才运行额外 physics settle；静态 navigation/articulation 不默认推进 30 步。
- 成功条件包含场景专属几何时，才逐 Scene 做正反例；共享的数值阈值或状态机逻辑只测试一次代表实例。
- 修改共享 primitive 时，按不同消费方式各选一个直接消费者；只有定向结果表明影响无法隔离时才扩大范围。
- 整个房间、整个 catalog 或全仓库的运行时回归只在用户明确要求时执行。

已经通过的验证只在后续代码再次改变运行时行为时重跑。文档、语言、注释、格式化以及不改变行为的重构不应触发重复 reset。

### 10.3 GUI、人工操作与数据采集

GUI 和数据采集不是一般任务设计的默认完成门槛。仅在用户明确要求，或本次目标是 viewer/teleop/采集就绪、视觉反馈或实际控制可达性时执行：

- 人工完成一次即可；只有 reset 行为本身被修改或用户要求时，才在同一实例完成第二次。
- 复合任务若需要人工验证，只检查一个正确顺序和一个关键错误顺序，不做所有排列。
- 未运行 GUI 或采集时，在结论中写“未验证/未采集”，不能把 headless 结果冒充人工证据，也不因此阻塞其他已完成的自动验收。
- 数据采集脚本适配与正式数据采集作为独立工作项维护，不随每次任务代码改动自动执行。

## 11. 交付结论格式

结论只汇报本次新增或修改的任务，不重复列出旧任务的历史验证。简单场景扩展、spec 调整或局部阈值修改使用默认精简格式：

```markdown
## 任务设计检查结论

- 改动：任务、Scene 和行为变化。
- 自动验证：实际运行的最小命令、次数与结果。
- 未验证项：GUI、采集或其他未执行项目；没有则写“无”。
- 风险：仍存在的具体风险；没有则写“无已知阻塞”。

最终结论：可实现 / 需修改设计 / 阻塞
```

只有新建复杂任务、修改共享 primitive、引入自由物体/随机布局，或新增复合状态机时，才使用详细格式：

```markdown
## 任务设计检查结论

- 任务定义：[x]/[ ]/N/A — 场景、类别、目标状态与顺序。
- 重复与注册：[x]/[ ]/N/A — 物理签名、已有入口、注册审计。
- 物理可行性：[x]/[ ]/N/A — fixture/joint、站位、障碍。
- 初始化与成功：[x]/[ ]/N/A — reset、正例和关键反例。
- 复合顺序：[x]/[ ]/N/A — 仅复合任务填写。
- 兼容性：[x]/[ ]/N/A — 直接受影响的旧行为。
- 自动验证：[x]/[ ]/N/A — 定向命令与结果。
- 未验证项：[ ]/N/A — GUI、采集或明确跳过的高成本检查。

未解决问题与风险：...
最终结论：可实现 / 需修改设计 / 阻塞
```
